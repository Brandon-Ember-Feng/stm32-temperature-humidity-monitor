# 测试计划 · STM32 温湿度监测仪

> 对应《岗位适配升级方案》事项 2.2。本文档按「测试项 / 测试方法 / 通过准则」三列组织，
> 实际结果由 `make test` 自动产出，不手工记录。

---

## 1. 目的与范围

### 1.1 为什么只测这几个模块

固件里「必须碰硬件」的部分（GPIO 时序、SPI 收发、定时器中断）只能在真机上验证，
在 PC 上没有意义。但**协议解析与数据处理是纯逻辑**，与硬件无关 —— 这部分如果不测，
一旦出错只能在真机上靠串口打日志猜：

| 模块 | 内容 | 为什么值得测 |
|---|---|---|
| `Util/filter.c` | 5 点滑动平均 | 边界多：窗口未满 / 已满 / 滚动覆盖，写错一个就是长期偏差 |
| `Util/fixed_str.c` | 定点数转字符串（替代 `sprintf`） | 手写取余拆位，小数与负号极易错位 |
| `Drivers/dht11_frame.c` | 40 位帧 → 温湿度 | **校验和是数据可信的唯一防线**，失效则显示"看起来合理的错误值" |
| `Drivers/hist_index.c` | 逻辑序号 → Flash 物理地址 | 双扇区乒乓后物理序与逻辑序不一致，跨扇区翻转那一步最易算错 |
| `Drivers/esp_parse.c` | AT 应答关键词匹配 | 串口是字节流，粘包 / 半截关键词 / 越界读都是真实风险 |

### 1.2 可测试性是怎么保证的

这五个模块**全部不 include 任何 `bsp_*.h`**，因此能在 PC 上用宿主编译器直接编译。
这不是巧合，而是分层约束（依赖单向 + 寄存器隔离）的直接结果：

- **规则 2（寄存器隔离）**：寄存器访问只允许出现在 `BSP/`，
  所以 `Drivers/` 与 `Util/` 里的逻辑天然不依赖硬件地址；
- **测试编译命令只给 `-IUtil -IDrivers`，不给 `-IBSP`**：
  万一有人往被测文件里加了硬件依赖，PC 端会立刻编译失败 ——
  边界由构建配置守着，不需要额外写检查规则。

为了做到这一点，有 3 处逻辑从「硬件流程」里被剥离出来成了独立文件（同一次改造）：

| 从哪剥离 | 抽成 | 原因 |
|---|---|---|
| `dht11.c` 的校验和判定 + `app.c` 的温湿度换算 | `Drivers/dht11_frame.c` | 时序驱动没法测，但位运算可以 |
| `hist_store.c` 中 `W25_RecRead` 的排序寻址段 | `Drivers/hist_index.c` | 纯算术，与 Flash 读写无关 |
| `esp8266_at.c` 的 `ESP_MatchAt` / `ESP_Has` | `Drivers/esp_parse.c` | 匹配逻辑与串口缓冲无关，输入改成 `(buf, len)` |

## 2. 测试环境

| 项 | 说明 |
|---|---|
| 运行位置 | 开发机（PC），不在目标板上 |
| 编译器 | 宿主编译器：CI / Linux / macOS 用 `cc`（gcc/clang）；Windows 上用 `zig cc`（兼容 gcc 命令行） |
| 编译选项 | `-std=c11 -Wall -Wextra -O1 -g`，要求**零警告** |
| 框架 | 自写轻量断言框架（`test/framework.h`，约 100 行，零依赖） |
| 规模 | 5 个套件、45 个用例、137 条断言 |

> 框架之所以自己写而不是用 Unity：每一行都讲得清 —— 断言失败怎么定位、
> 宏展开成什么。整个框架不依赖被测工程的任何代码。

## 3. 测试项清单

### 3.1 `Util/filter.c` —— 滑动平均（8 项）

| 编号 | 测试项 | 方法 | 通过准则 |
|---|---|---|---|
| UT-FLT-01 | 初始化清零 | 先塞脏数据（idx/cnt/buf）再 `Filter_Init` | `Count=0`，`Avg=0`（不除零） |
| UT-FLT-02 | 单个样本 | 推入 1 个值 | `Count=1`，`Avg=该值` |
| UT-FLT-03 | **窗口未满按实际个数** | 推入 3 个（300/320/280） | `Avg=300`（900/3，若错除 FILTER_N 会得 180） |
| UT-FLT-04 | 窗口刚好满 | 推入 300/320/280/310/290 | `Avg=300`（1500/5） |
| UT-FLT-05 | **滚动覆盖丢最旧** | 推满后再推 600、700 | `Avg` 依次为 400、500；`Count` 封顶为 5 |
| UT-FLT-06 | 负值（零下温度） | 推入 −100、−200 | `Avg=−150` |
| UT-FLT-07 | 整数除法截断方向 | 推入 1、2 与 −1、−2 | 得 1 与 −1（向零取整，不是向下） |
| UT-FLT-08 | 计数不溢出 | 连续推入 200 个 | `Count` 仍为 `FILTER_N` |

| 编号 | 测试项 | 方法 | 通过准则 |

### 3.3 `Drivers/dht11_frame.c` —— 帧解码（9 项）

| 编号 | 测试项 | 方法 | 通过准则 |
|---|---|---|---|
| UT-DHT-01 | 正常帧 | 65/0/25/6，校验和 96 | 校验通过；湿度 650，温度 256 |
| UT-DHT-02 | 小数位非 0 | 65/5/25/6 | 湿度 655（兼容其他型号） |
| UT-DHT-03 | **校验和错必须被拒** | 校验和 +1；数据 +1 | 两种情况均返回 0 |

| UT-DHT-05 | 全 0 帧 | 5 字节全 0 | 校验**通过**（0==0，数学合法），温湿度为 0；此边界在文档中说明 |

| UT-DHT-07 | 负温 | 温度字节 `0x80\|10` | 温度 = −105（−10.5），湿度 500 |

| UT-DHT-09 | 零下 1 度 | 温度字节 `0x80\|1` | 温度 = −10（−1.0，不能算成 0） |

### 3.4 `Drivers/hist_index.c` —— 记录寻址（8 项）

| 编号 | 测试项 | 方法 | 通过准则 |
|---|---|---|---|
| UT-HIS-01 | 仅扇区 A 有数据 | cnt_a=10, cnt_b=0 | idx 0…9 落在 A；idx=10 越界 |
| UT-HIS-02 | 仅扇区 B 有数据 | cnt_a=0, cnt_b=5 | idx 0 落在 B 起始+4 |

### 3.5 `Drivers/esp_parse.c` —— AT 应答匹配（11 项）

| 编号 | 测试项 | 方法 | 通过准则 |
|---|---|---|---|
| UT-ESP-01 | 基本查找 | 在 `"AT\r\nOK\r\n"` 找 `OK` / `ERROR` / `AT` | 命中 / 不命中 / 命中 |
| UT-ESP-02 | **粘包：半截关键词** | 缓冲为 `"AT\r\nO"`、`"AT\r\nOK"` | 前者不命中，后者命中 |
| UT-ESP-03 | 指定位置匹配 | 从索引 4 / 3 匹配 `OK` | 前者命中，后者不命中 |
| UT-ESP-04 | 末尾半截不收 | `"xxO"` 匹配 `OK` | 不命中 |
| UT-ESP-05 | **绝不越界读** | 定长数组 `"OKOKOKOK"`，len 依次取 1 / 2 / 8 | len=1 不命中；len=2 命中（证明只读 len 之内） |
| UT-ESP-06 | 空输入 / 空关键词 | len=0；token 为空串 | 不命中；空串按约定返回命中 |
| UT-ESP-07 | 重叠匹配 | `"OOOK"` 找 `OK` | 命中 |
| UT-ESP-08 | token 比缓冲长 | `"OK"` 找 `OKOKOK` | 不命中 |
| UT-ESP-09 | 单字符 token | `"AT+CIPSEND=4\r\n> "` 找 `>` | 命中 / 不命中 |
| UT-ESP-10 | 真实 AT 应答 | `0,CONNECT` / `0,CLOSED` / `WIFI GOT IP` / `ERROR` / `busy p...` / `link is not valid` | 各自关键词命中，交叉关键词不命中 |
| UT-ESP-11 | 同时含两个关键词 | 缓冲中先 CLOSED 后 CONNECT | 两个都找得到 |

## 4. 未覆盖的部分（已知缺口）

诚实列出来，避免"测试全绿等于没问题"的误判：

| 未覆盖 | 原因 | 现在的替代验证手段 |
|---|---|---|
| DHT11 单总线时序 | 依赖微秒级 GPIO 翻转，PC 上无法复现 | 真机实测 + 串口打印错误步号（1~6） |
| 软件 I2C / SPI 时序 | 同上 | 真机上电自检（OLED 点亮、`JEDEC ID = 0xEF4017`） |
| USART2 接收中断 | 并发行为，需要硬件 | 真机长跑 + 断线重连观察 |
| TIM2 时基 / 中断嵌套 | 需要真实中断源 | 串口打印运行时间做对比 |
| OLED 显示排版 | 像素级输出，只能看屏幕 | 人工目视检查（行号只能是 0/2/4/6） |
| 掉电时 Flash 记录一致性 | 需要可控断电 | 双扇区乒乓设计本身提供的容错 |
| 端到端集成（串口日志断言） | 需要板子接着电脑 | **规划中**：`test/integration/` 用 pyserial 自动断言串口关键行 |

## 5. 如何执行

```bash
# 架构校验 + 编译并运行全部单元测试（一条命令）
make test

# 只跑架构校验
make check-layering

# 指定宿主编译器（Windows 上没有 cc 时）
make test HOSTCC="zig cc"
```

- 全部通过：退出码 **0**，末行 `RESULT: PASS`
- 有任何用例失败：退出码 **1**，并打印**第一条**失败断言的 `文件:行号` 与期望/实际值

CI（`.github/workflows/ci.yml`）在每次 push 时自动执行：
① 架构校验 → ② 交叉编译固件（`-Wall -Wextra` 零警告门槛）→ ③ 本计划全部用例。

## 6. 测试有效性验证

测试本身也需要被验证 —— 否则"全绿"可能只是断言写错了。做法是**故意注入 bug**：

| 注入的缺陷 | 预期 | 实测 |
|---|---|---|
| `Filter_Avg` 改为固定除以 `FILTER_N`（窗口未满时也除 5） | 相关用例失败 | **4 个用例失败，退出码 1** ✓ |

恢复后重新执行即全部通过。这条验证说明：断言确实能区分正确与错误实现，
而不是"恒真"。

> 说明：这只覆盖了"测试能抓到这个错误"，不等于覆盖了所有可能的缺陷。
> 更系统的做法（变异测试）在本项目规模下没有引入。
