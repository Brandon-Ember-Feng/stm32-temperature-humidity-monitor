## 1. 目的与范围

### 1.1 为什么要区分"能测的"和"不能测的"

固件里「必须碰硬件」的部分（GPIO 时序、SPI 收发、定时器中断）只能在真机上验证，在 PC 上没有意义 —— 强行搬进单测只会得到一堆"因为环境不对而失败"的假信号。

但**协议解析与数据处理是纯逻辑**，与硬件无关。这部分如果不测，一旦出错只能在真机上靠串口打日志猜，而嵌入式里最贵的就是"猜"。

| 模块 | 内容 | 为什么值得测 |
|---|---|---|
| `Util/filter.c` | 5 点滑动平均 | 边界多：窗口未满 / 已满 / 滚动覆盖，写错一个就是长期偏差 |
| `Util/fixed_str.c` | 定点数转字符串（替代 `sprintf`） | 手写取余拆位，小数与负号极易错位 |
| `Drivers/dht11_frame.c` | 40 位帧 → 温湿度 | **校验和是数据可信的唯一防线**，失效则显示"看起来合理的错误值" |
| `Drivers/hist_index.c` | 逻辑序号 → Flash 物理地址 | 双扇区乒乓后物理序与逻辑序不一致，跨扇区翻转那一步最易算错 |
| `Drivers/esp_parse.c` | AT 应答关键词匹配 | 串口是字节流，粘包 / 半截关键词 / 越界读都是真实风险 |

**测试范围**：上述 5 个模块的 **15 个公开函数**，共 **45 个用例 / 137 条断言**。

**范围外**：其余模块（总线时序、中断服务、OLED 排版）的验证方式见 §5。

### 1.2 三个判断标准（决定一个函数该不该进单测）

| 标准 | 归入"可测" | 归入"不可测" |
|---|---|---|
| 输入输出是否只由参数决定 | 是（纯函数） | 否（依赖引脚状态、寄存器） |
| 是否需要精确时序 | 否 | 是（单总线、软件 I2C、SPI 位时序） |
| 失败是否只由算法决定 | 是（越界、溢出、取整方向） | 否（总线无应答、超时） |

### 1.3 可测试性是怎么保证的

这五个模块**全部不 include 任何 `bsp_*.h`**，因此能在 PC 上用宿主编译器直接编译。这不是巧合，而是分层约束（依赖单向 + 寄存器隔离）的直接结果：

- **规则 2（寄存器隔离）**：寄存器访问只允许出现在 `BSP/`，所以 `Drivers/` 与 `Util/` 里的逻辑天然不依赖硬件地址；
- **测试编译命令只给 `-IUtil -IDrivers`，不给 `-IBSP`**：万一有人往被测文件里加了硬件依赖，PC 端会立刻编译失败 —— **边界由构建配置守着，不需要额外写检查规则**。

为了做到这一点，有 3 处逻辑从「硬件流程」里被剥离出来成了独立文件（同一次改造，逻辑一行未改，只换了位置）：

| 从哪剥离 | 抽成 | 原因 |
|---|---|---|
| `dht11.c` 的校验和判定 + `app.c` 的温湿度换算 | `Drivers/dht11_frame.c` | 时序驱动没法测，但位运算可以 |
| `hist_store.c` 中 `W25_RecRead` 的排序寻址段 | `Drivers/hist_index.c` | 纯算术，与 Flash 读写无关 |
| `esp8266_at.c` 的 `ESP_MatchAt` / `ESP_Has` | `Drivers/esp_parse.c` | 匹配逻辑与串口缓冲无关，输入改成 `(buf, len)` |

## 2. 测试策略

### 2.1 分层测试策略

| 层级 | 手段 | 覆盖对象 | 执行频率 |
|---|---|---|---|
| L1 静态检查 | `tools/check_layering.py` | 三条分层约束（49 个文件） | 每次编译前 |
| L2 编译期检查 | `-Wall -Wextra` + **零警告门槛** | 全部源码 + 测试代码 | 每次编译、每次 push |
| L3 单元测试 | `make test`（PC 端） | 5 个纯逻辑模块，45 用例 | 每次 `make test`、每次 push |
| L4 实物验证 | 上电自检 + 串口日志 + 目视 | 时序、中断、排版、端到端 | 每次烧录后 |

**为什么 L2 也是测试**：嵌入式里的警告往往就是真 bug（未初始化变量、隐式类型截断、有符号/无符号比较）。把"零警告"做成硬门槛，等于免费得到一层静态缺陷检测。

### 2.2 用例设计原则

| 原则 | 做法 |
|---|---|
| 边界优先于常规 | 窗口未满 / 恰好满 / 越界 / 序号相等 / 全 `0xFF`，这些比"正常值"更有价值 |
| 错误路径必须有用例 | 校验和错、负温、半截关键词、token 比缓冲长 |
| 用"不合法输入"撞实现 | `test_never_reads_past_length` 用**不含 `'\0'`** 的定长数组，逼实现只依赖 `len` |
| 断言要能区分对错实现 | 通过注入 bug 反向验证（见 §6） |
| 不测"实现细节" | 断言公共接口的返回值，不断言内部变量 |

### 2.3 通过准则

- **单元测试**：45 个用例全部通过，退出码 0，末行 `RESULT: PASS`
- **警告门槛**：编译输出中 `grep -qi "warning:"` 无命中
- **架构校验**：3 条规则全部 ✔
- 三者同时满足才算通过

## 3. 测试环境

| 项 | 说明 |
|---|---|
| 运行位置 | 开发机（PC），**不在目标板上** |
| 宿主编译器 | CI / Linux / macOS 用 `cc`（gcc/clang）；Windows 上用 `zig cc`（zig 0.13.0，完全兼容 gcc 命令行） |
| 交叉编译器 | arm-none-eabi-gcc 14.3（CubeIDE 自带）用于固件编译 |
| 编译选项 | 测试：`-std=c11 -Wall -Wextra -O1 -g`；固件：`-mcpu=cortex-m3 -mthumb -std=c11 -Wall -Wextra -O1 -g` |
| 框架 | 自写轻量断言框架（`test/framework.h`，约 100 行，零依赖） |
| 规模 | 5 个套件、45 个用例、137 条断言 |

> 框架之所以自己写而不是用 Unity / CMocka：**每一行都讲得清** —— 断言失败怎么定位、宏展开成什么。
> 整个框架不依赖被测工程的任何代码，也不引入第三方依赖（CI 上不需要额外下载）。

**框架的三个设计点**：

1. `TF_STR2/TF_STR1/TF_LOC` 辅助宏把 `__LINE__` 展开成字符串 `"文件:行号"`，失败时能直接定位；
2. `TF_FAIL` 只保存**第一条**失败详情（`tf_first_fail_at` / `tf_first_fail_msg[256]`）—— 避免后续失败淹没根因；
3. 输出刻意用**英文**：Windows 控制台默认 GBK 代码页，UTF-8 中文会乱码，而 CI 是 UTF-8。用英文两边都正常。

| 编号 | 测试项 | 方法 | 通过准则 |
|---|---|---|---|
| UT-HIS-01 | 仅扇区 A 有数据 | cnt_a=10, cnt_b=0 | idx 0…9 落在 A；idx=10 越界 |
| UT-HIS-02 | 仅扇区 B 有数据 | cnt_a=0, cnt_b=5 | idx 0 落在 B 起始+4 |
| UT-HIS-03 | B 更新（A 为旧） | cnt_a=3, cnt_b=2, seq_b 较大 | idx 0…2 在 A；**idx=3 起翻到 B**；idx=5 越界 |
| UT-HIS-04 | A 更新（B 为旧） | cnt_a=2, cnt_b=4, seq_a 较大 | idx 0…3 在 B；idx=4 起翻到 A；idx=6 越界 |
| UT-HIS-05 | **满载边界** | 两扇区各 1364 条（共 2728） | idx 1363 在 A 末条且地址 < A+4096；idx 1364 起在 B；idx 2727 在 B 末条；idx 2728 越界 |
| UT-HIS-06 | 序号相等 | cnt_a=0, seq_a=seq_b | 走单扇区分支，落在 B |
| UT-HIS-07 | 存储全空 | 两扇区条数均为 0 | 任何 idx 都越界，不返回合法地址 |
| UT-HIS-08 | 旧扇区仅 1 条 | cnt_a=1, cnt_b=4 | idx 0 在 A，idx 1 立刻翻到 B |

> UT-HIS-05 是这一组里价值最高的一条：它同时验证了**跨扇区翻转点**（1363/1364）、
> **末条边界**（2727）、**越界拒绝**（2728），并额外断言地址不越过扇区边界
> （`addr < sector_start + 4096`）—— 后一条断言能抓到"地址算过了头、写到下一个扇区去"这类隐蔽缺陷。

### 4.5 `Drivers/esp_parse.c` —— AT 应答匹配（11 项）

| 编号 | 测试项 | 方法 | 通过准则 |
|---|---|---|---|
| UT-ESP-01 | 基本查找 | 在 `"AT\r\nOK\r\n"` 找 `OK` / `ERROR` / `AT` | 命中 / 不命中 / 命中 |
| UT-ESP-02 | **粘包：半截关键词** | 缓冲为 `"AT\r\nO"`、`"AT\r\nOK"` | 前者不命中，后者命中 |
| UT-ESP-03 | 指定位置匹配 | 从索引 4 / 3 匹配 `OK` | 前者命中，后者不命中 |
| UT-ESP-04 | 末尾半截不收 | `"xxO"` 匹配 `OK` | 不命中 |
| UT-ESP-05 | **绝不越界读** | 定长数组 `"OKOKOKOK"`，len 依次取 1 / 2 / 8 | len=1 不命中；len=2 命中（证明只读 len 之内） |
| UT-ESP-06 | 空输入 / 空关键词 | len=0；token 为空串 | 不命中；空串按约定返回命中 |
| UT-ESP-07 | 重叠匹配 | `"OOOK"` 找 `OK` | 命中 |
| UT-ESP-08 | token 比缓冲长 | `"OK"` 找 `OKOKOK` | 不命中 |
| UT-ESP-09 | 单字符 token | `"AT+CIPSEND=4\r\n> "` 找 `>` | 命中 / 不命中 |
| UT-ESP-10 | 真实 AT 应答 | `0,CONNECT` / `0,CLOSED` / `WIFI GOT IP` / `ERROR` / `busy p...` / `link is not valid` | 各自关键词命中，交叉关键词不命中 |
| UT-ESP-11 | 同时含两个关键词 | 缓冲中先 CLOSED 后 CONNECT | 两个都找得到 |

> UT-ESP-05 的构造方式值得说明：数组**故意不含 `'\0'`**。
> 这逼实现只能依赖传入的 `len`，而不能像原来那样依赖缓冲区末尾的结束符 ——
> 正是这条用例暴露并保住了 §1.3 里提到的那个真实隐患。

## 5. 未覆盖的部分（已知缺口）

诚实列出来，避免"测试全绿等于没问题"的误判：

| 未覆盖 | 原因 | 现在的替代验证手段 | 风险等级 |
|---|---|---|---|
| DHT11 单总线时序 | 依赖微秒级 GPIO 翻转，PC 上无法复现 | 真机实测 + 串口打印错误步号（1~6） | 中 |
| 软件 I2C / SPI 时序 | 同上 | 真机上电自检（OLED 点亮、`JEDEC ID = 0xEF4017`） | 中 |
| USART2 接收中断 | 并发行为，需要硬件 | 真机长跑 + 断线重连观察；200 帧连续推送压测 | 中 |
| TIM2 时基 / 中断嵌套 | 需要真实中断源 | 串口打印运行时间与秒表对比 | 低 |
| OLED 显示排版 | 像素级输出，只能看屏幕 | 人工目视检查（行号只能是 0/2/4/6）；行号越界已由 `if (page > 6U) return` 保护 | 低 |
| 掉电时 Flash 记录一致性 | 需要可控断电 | 双扇区乒乓设计本身提供的容错（逻辑推理） | **中高** |
| 端到端集成（串口日志断言） | 需要板子接着电脑 | **规划中**：`test/integration/` 用 pyserial 自动断言串口关键行 | 中 |
| 行覆盖率 / 分支覆盖率 | 未引入 gcov | 改为"公开函数 100% 被用例直接调用"这一弱化指标 | 低 |

> **风险等级最高的一项**是"掉电一致性"：它是整个 v1.2 里最复杂的设计（双扇区乒乓 + 序号对账），
> 但验证方式只有"设计推理"，没有实机反复断电试验。这是本项目最值得优先补上的验证项。

## 6. 测试有效性验证

测试本身也需要被验证 —— 否则"全绿"可能只是断言写错了、或者压根没跑到。

做法是**故意注入 bug**，看断言能不能抓到：

| 注入的缺陷 | 预期 | 实测 |
|---|---|---|
| `Filter_Avg` 改为固定除以 `FILTER_N`（窗口未满时也除 5） | 相关用例失败 | **4 个用例失败，退出码 1** ✓ |

恢复正确实现后重新执行即全部通过。这条验证说明：**断言确实能区分正确与错误实现**，而不是"恒真"。

> 说明：这只覆盖了"测试能抓到这个错误"，不等于覆盖了所有可能的缺陷。
> 更系统的做法（变异测试 / mutation testing）在本项目规模下没有引入 ——
> 引入它需要自动化地批量注入并统计"杀死率"，成本高于收益。

| **合计** | **15** | **15（100%）** | **45** | **137** |

**未统计**：行覆盖率与分支覆盖率（未引入 gcov）。当前使用的替代指标是"公开函数 100% 被直接调用" —— 这是一个**弱化指标**，只说明"没有完全没被摸过的接口"，不能说明"每条分支都被走到"。

### 7.3 本轮的缺陷发现记录

测试与校验体系在本轮改造中实际抓到的问题：

| # | 缺陷 | 发现方式 | 严重度 | 处理 |
|---|---|---|---|---|
| 1 | **极值统计从未生效**：`g_temp_min/max`、`g_humi_min/max` 只声明未赋值，极值画面恒显示 3276.7 / −3276.8 | 重构的**等价性校验**（逐函数比对时发现 4 个变量在重构前后都没有写入点） | 高（功能完全不可用） | 已修复，并在 `app.c` 留下修复注释；已列入实物回归项 |
| 2 | **`ESP_Has` 依赖缓冲区末尾的 `'\0'`**：USART2 是定长缓冲，可能刚好填满而无结束符 → 越界读 | 逻辑剥离时的**接口重设计**（被迫把 `len` 显式传入） | 中（偶发、难复现） | 已修复；新增 UT-ESP-05 用不含 `'\0'` 的数组守住 |
| 3 | **Makefile 在 Windows 上 `make` 随机失败**（报 `make (e=87): 参数错误`，且每次失败的文件不同） | 构建期实测 | 中（阻断开发，且极具迷惑性） | 已修复：显式给 `SHELL` 赋值为 Git for Windows 的 sh，绕开 PATH 里的假 sh shim |
| 4 | **分层校验的 `> /dev/null` 重定向依赖具体 shell** | 同一问题的连带发现 | 低 | 已改为 order-only 依赖，不再依赖重定向 |

> 缺陷 1 是本轮最有价值的产出：它说明**"代码能编译、能跑、画面能显示"不等于功能正确** ——
> 极值画面一直在显示一个"看起来像数字"的错误值（3276.7），
> 如果不做逐函数等价性比对，这个 bug 会一直留在"已完成"的功能清单里。
>
> 缺陷 2 说明**善意的重构（为了可测试性而剥离）常常会顺带暴露真实隐患** ——
> 因为剥离迫使你重新思考接口边界，而原来"依赖 `'\0'`"这件事在旧代码里是隐式的。

### 7.4 残余风险

| 风险 | 影响 | 缓解措施 | 建议 |
|---|---|---|---|
| 掉电一致性未实测 | 极端情况下可能丢更多记录 | 双扇区乒乓设计 | 优先补：可控断电重复试验 |
| 记录序号 uint16 回绕（≈1090 小时） | 一轮排序颠倒 | 演示场景不会触发 | 产品化时扩到 4 字节或在 init 时归一化 |
| 湿度记录限幅到 255（25.5 %） | 高湿区间精度丢失 | 历史画面只看趋势 | 如需精确记录，记录长度扩到 4 字节 |
| 时序正确性无自动化验证 | 换芯片/改时钟后可能静默失效 | 上电自检 + 串口日志 | 有条件时用逻辑分析仪做一次时序基线 |
| 无硬件看门狗 | 程序跑飞后无法自恢复 | 无 | 建议加 IWDG（成本极低） |

## 8. 如何执行

```bash
# 架构校验 + 编译并运行全部单元测试（一条命令）
make test

# 只跑架构校验
make check-layering

# 指定宿主编译器（Windows 上没有 cc 时）
make test HOSTCC="zig cc"
```

- 全部通过：退出码 **0**，末行 `RESULT: PASS`
- 有任何用例失败：退出码 **1**，并打印**第一条**失败断言的 `文件:行号` 与期望/实际值

**CI 自动执行**（`.github/workflows/ci.yml`，每次 push / PR）：

| 步骤 | 门槛 |
|---|---|
| ① `python3 tools/check_layering.py` | 3 条规则全部通过 |
| ② `make TOOLCHAIN=/usr/bin` | 交叉编译成功，**且 `grep -qi "warning:"` 无命中** |
| ③ `make test` | 45 个用例全部通过，**且测试代码零编译警告** |

CI 中特意用了 `set -o pipefail` —— 否则管道的退出码来自 `tee`，会掩盖 `make` 的失败。
