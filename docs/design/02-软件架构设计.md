## 1. 架构目标

架构不是"把文件分几个文件夹"，而是**为了得到某些属性而主动付出的代价**。本项目的架构由四个目标驱动，按优先级排列：

| 优先级 | 目标 | 为什么重要 | 对应手段 |
|---|---|---|---|
| 1 | **可测试性**：核心逻辑能脱离硬件在 PC 上验证 | 嵌入式最大的效率瓶颈是"改一行代码要烧一次板子"。不解决这个，测试成本高到不会有人去做 | 寄存器隔离在 `BSP/`；纯逻辑剥离成独立文件 |
| 2 | **外设独立性**：任一外设故障不扩散 | 6 个外设里任何一个接触不良都很常见，不能因为 Flash 没接好就整机不工作 | 分层 + 每个外设上电自检 + 独立的就绪标志 |
| 3 | **可维护性**：改一处不牵动全身 | 项目要持续迭代（v1.0 → v1.2 之间改了 3 轮），改动影响面必须可预测 | 依赖单向 + 接口收敛 |
| 4 | **可移植性**：换芯片只改一层 | 换到 F4 / GD32 / 国产替代时，业务逻辑不该重写 | 全部寄存器访问集中在 `BSP/` |

**非目标**（有意不做的）：

- **不是**为了代码好看或分层而分层 —— 分层是手段，可测试性才是目的
- **不是**为了追求极致性能 —— 分层带来约 1 KB 额外 Flash 开销，这对 64 KB 的芯片是可以接受的代价；真正的性能敏感路径（DHT11 时序）仍保留在直接操作引脚的实现里
- **不是**为了通用化 —— 没有做成"能适配所有传感器"的框架，过度抽象在小项目里是负收益

### 2.1 各层职责边界

| 层 | 负责 | 不负责 | 允许 include |
|---|---|---|---|
| `Core/` | 主循环调度、数据模型、报警判定、画面组织、上电自检顺序 | 任何寄存器、任何总线时序 | 全部下层 |
| `Drivers/` | 器件协议与指令、驱动内部状态维护、错误码 | 引脚配置、总线电平时序、界面排版 | `BSP/`、`Util/` |
| `BSP/` | 寄存器读写、时钟树、GPIO 配置、总线时序、中断服务 | 器件协议（不知道"DHT11"是什么） | `bsp_reg.h`、`Util/` |
| `Util/` | 纯算术与纯字符串格式化 | 任何硬件相关操作 | 仅 C 标准库 |

> **边界的一个具体体现**：`Drivers/dht11.c` 里写的是"拉低 20 ms 发起始信号、读 40 位、验校验和"（协议），
> 而"把某个引脚置 0 需要写哪个寄存器"在 `BSP/bsp_onewire.c`（物理层）。
> 换一根引脚只改 BSP；换一个单总线传感器只改 Drivers。

## 3. 三条硬性约束及其强制手段

| # | 约束 | 为什么 | 违反会怎样 |
|---|---|---|---|
| **1** | **依赖单向**：`Core → Drivers → BSP → Util`，禁止反向 | 反向依赖（例如 `filter.c` include `bsp_gpio.h`）会让模块无法单独编译，测试价值归零，也制造循环依赖 | `tools/check_layering.py` 报错并中断编译 |
| **2** | **寄存器隔离**：所有寄存器读写只允许出现在 `BSP/` | 上层不含硬件细节 ⇒ 把逻辑搬到 PC 上编译、跑单元测试才有可能。这是第 1 章"可测试性"的唯一前提 | 脚本检测到 `Drivers/`、`Core/` 中出现寄存器访问即报错 |
| **3** | **接口收敛**：`BSP/Util/Drivers` 的内部可变状态一律 `static`，跨模块只走 `.h` 中的访问函数 | "谁能改这个状态"永远只有一个答案；出问题时排查面从全工程缩到一个文件 | 脚本检测到非 `static` 的全局变量即报错 |

### 3.1 约束怎么被强制（而不是靠自觉）

三条约束由 `tools/check_layering.py` 在**每次编译前**自动检查，且被做成 Makefile 的 order-only 依赖：

```make
$(BUILD_DIR)/%.o: %.c | $(BUILD_DIR) check-layering
```

```bash
$ make check-layering
======================================================================
分层架构校验   共检查 49 个文件
======================================================================
  规则1 依赖单向   Core -> Drivers -> BSP -> Util   ✔
  规则2 寄存器隔离 寄存器访问仅存在于 BSP/ 层        ✔
  规则3 接口收敛   BSP/Util/Drivers 内部状态全 static ✔

结论：架构约束全部满足 ✔
```

三点设计细节：

1. **order-only 依赖**（`|`）保证校验在任何编译动作之前跑完，但它的时间戳不参与"这个 `.o` 要不要重建"的判断 —— 既守住了门槛，又不会因为校验而触发全量重编。
2. 校验放在 Makefile 里、而不是塞进每个 `.o` 的 recipe，是因为后者依赖具体 shell 的重定向行为（原实现用 `> /dev/null`，在 Windows 上会因为 shell 探测问题失败）。
3. `const` 只读数据不算违规 —— 规则 3 防的是"可变共享状态"，`const` 表（如字库）本来就是只读的。

### 3.2 第三条约束的实际收益

重构前，`Core/main.c` 会直接给驱动内部的变量干活：

```c
/* 重构前（上层在改驱动内部状态 —— 典型的分层穿越） */
g_spi_ok     = 1;
g_dht_ok_cnt++;
```

现在这些动作全部收在驱动内部，上层只能读结论：

```c
/* 重构后 */
if (W25_IsOk()) { ... }          /* 结论由驱动给，上层不再自己判定 */
DHT_OkCount();                    /* 统计由 DHT11_Read() 内部维护 */
```

价值有两层：① 排查"计数器为什么是 0"时只需看一个文件；② 上层**没有能力**改坏它 —— 漏一次调用导致计数永久失真的故障模式被从设计上消除了。

## 4. ★ 关键设计决策与取舍

> 列出「代价」是有意的。一个说不出代价的方案，通常意味着还没想清楚。
> 面试中这一段是重点：**能讲出代价，才说明这是主动选择而不是抄来的**。

| # | 决策 | 理由 | 代价 |
|---|---|---|---|
| D1 | **不用 HAL，直接写寄存器** | 每一行都对应参考手册的一个 bit，能看清外设真实工作方式；同时省下 HAL 的几十 KB Flash | 换芯片要重写整个 `BSP/`；没有 HAL 提供的参数校验，配错了不会报错，只会"不工作" |
| D2 | **代码分四层，寄存器只在 BSP** | 上层不含硬件细节，逻辑能在 PC 上编译并做单元测试；换芯片只改 `BSP/` | 多一层函数跳转与一次数据拷贝，实测多约 1 KB Flash；代码量比"一个文件写完"多 |
| D3 | **把可测逻辑剥离成独立文件，再上 PC 单元测试** | 硬件的正确性只能靠实机验证，但**算法的正确性可以靠断言**。两者分开后，改一行换算逻辑不必烧板子就知道对错 | 新增 3 个文件与一次数据拷贝（实测 +236 B Flash）；"什么该剥离"没有机械标准，依赖判断 |
| D4 | **规则 2 与 3 用脚本强制，而不是写文档** | 靠自觉的约束等于没有约束；文档会被忘，编译失败不会 | 多一个构建步骤和一个 Python 脚本依赖；脚本本身也可能误报，需要维护 |
| D5 | **用 HSI 内部时钟而非外部晶振** | 不依赖外部晶振是否起振，程序更"皮实"；也省两个引脚 | 精度约 ±1%，不适合长时间绝对计时。本项目只做相对计时（开机起算），够用 |
| D6 | **时基用 TIM2 硬件中断，不用延时累加** | 软件延时的每次调用都有指令开销，累加一万次误差明显；定时器由硬件计数触发，与程序在干什么无关 | 占用一个定时器（TIM2）；中断服务程序必须保持极短，否则影响单总线时序 |
| D7 | **SysTick 与 TIM2 分工使用** | `SysTick` 被 `delay_us/delay_ms` 借去当"一次性秒表"（用完即关），无法提供连续的"墙上时间"；因此系统时基另用 TIM2 | 两个定时器各管一件事，概念上略多；但换来"延时精度"和"时间连续性"互不干扰 |
| D8 | **Flash 用双扇区乒乓写入** | Flash 只能把 1 写成 0，改写前必须整扇区擦除。两扇区轮流用，寿命消耗极慢 | 有效容量减半；逻辑复杂度显著上升（要处理掉电、序号对账、跨扇区翻转）。且引入了序号回绕的已知边界 |
| D9 | **历史记录只存温湿度，不存时间戳** | 没有 RTC，存"开机后第几分钟"意义有限；序号 × 1 分钟已经能表达"趋势" | 记录无法与真实日期对应。若加 RTC 或 NTP 才需要扩展记录格式（记录长度变化 = 存储格式变更） |
| D10 | **USART2 接收用中断而非轮询** | 115200 下字节间隔仅 87 µs，主循环 10 ms 才轮询一次，**慢两个数量级**；硬件接收寄存器只能存 1 字节，第 2 个字节到来时前一个还没读走就丢弃 | 多一个中断服务程序；缓冲与游标的并发访问要小心（清缓冲时必须关中断） |
| D11 | **单总线读取期间关全局中断** | DHT11 用"高电平 28 µs 还是 70 µs"编码 0/1，判据是延时 40 µs 后采样。TIM2 每 1 ms 中断一次，ISR 执行几微秒就会把采样点推迟，极端情况把 1 读成 0 | 一次读取约 24 ms 时基不累加，占 2 秒周期的 1.2%。对"显示运行时间"用途可接受，对精确计时不可接受 |
| D12 | **ESP-01S 自建热点，而非连路由器** | 不依赖外部网络和现场 WiFi，演示时随手就能连；也规避了配网流程 | 热点无外网，手机/电脑会提示"无法访问互联网"；只能局域网内查看，无法远程 |
| D13 | **ESP 配置与发送是阻塞的** | AT 指令是严格的一问一答（尤其 `CIPSEND` 的三步握手不能插别的指令），非阻塞化收益低、复杂度高 | 一帧推送约 300 ms 阻塞主循环；解决方案是"仅在有客户端时推送"，无客户端直接跳过，不白等超时 |
| D14 | **主循环按 10 ms 步进切片，而不是 `delay_ms(2000)` 死等** | 原来 2 秒死等期间按键按下去最多等 2 秒才有反应。切片后在每 10 ms 缝隙里扫按键、翻 LED、维护 ESP，按键延迟降到约 10 ms | 主循环结构比"读一次、延时两秒"复杂；需要把周期性动作（LED 翻转、蜂鸣器节拍、时间刷新）都做成"借 `BSP_Millis()` 判相位"的形式 |
| D15 | **不用 `sprintf` / 浮点，手写定点格式化** | Flash 只有 64 KB，`sprintf` 会拖进整个格式化引擎；浮点还要软件模拟 | 只能按固定格式输出，格式改了要改代码；`Util/fixed_str.c` 需要自己写和测试 |
| D16 | **数值统一用 ×10 定点整数** | 避免浮点；一位小数对温湿度足够 | 所有算术要考虑缩放因子；显示、存储、推送三处格式必须一致（都由 `fixed_str` 负责，避免各写一份） |
| D17 | **不使用动态内存 / RTOS** | 长期运行不容许碎片化；任务数量少、时序简单，裸机主循环 + 中断足够 | 无法在运行期调整缓冲区大小；新增"重任务"时需要手工切时间片。若将来接 Modbus 主站轮询多从站，可能要重新评估 |
| D18 | **驱动暴露"结论"，不暴露"账本"** | 上层关心"有几条记录"，不关心"扇区头怎么解析"。18 个只读访问函数把跨模块状态收口 | 每个状态多一个函数调用；新增状态要同步加接口，略显啰嗦 |
| D19 | **构建走 Makefile，同时保留 CubeIDE 工程** | Makefile 才能接进 CI（GitHub Actions 上跑不了 IDE）；CubeIDE 工程方便日常调试与断点 | 两份构建配置需要保持同步（源码目录列表若不一致，会出现"命令行能编、IDE 编不过"） |
| D20 | **测试的门槛是"零警告"，不只是"零失败"** | 嵌入式里的警告往往就是真 bug：未初始化变量、隐式类型截断、有符号/无符号比较 | 升级编译器版本时旧代码可能突然"有警告"而导致 CI 红。这是有意的：宁可显式处理，也不要带着隐患 |

## 5. 运行时数据流

```
                      ┌─────────────────────────┐
                      │  TIM2 中断 @1 kHz       │
                      │  g_ms_tick++            │
                      └───────────┬─────────────┘
                                  │ BSP_Millis()
                                  ▼
   ┌──────────────────────────────────────────────────────────┐
   │  Core/main.c   主循环（while(1)）                         │
   │                                                          │
   │  ① DHT11_Read()  ──────────────────────────────┐          │
   │  │   Drivers/dht11.c  ── 时序 ── BSP/bsp_onewire.c        │
   │  │   成功：40 位 → dht11_frame.c 校验和/解码              │
   │  │   失败：错误码 1~6，进 OLED/串口                        │
   │  ▼                                                       │
   │  ② DHT_Process()   Core/app.c                            │
   │  │   raw[5] → 温度/湿度(x10) → Filter_Push                │
   │  │   → Filter_Avg → g_xxx_avg（显示/存储/推送的统一数据源）│
   │  │   → 更新极值 → 判报警 g_alarm                          │
   │  ▼                                                       │
   │  ③ DHT_PrintUart()   → USART1 日志                       │
   │  ④ OLED_Refresh()    → 按 g_mode 重绘                    │
   │                                                          │
   │  ⑤ 每隔 60 s：Hist_IsReady() → W25_RecAppend()           │
   │  │   Drivers/hist_store.c → W25_PageProgram → SPI1       │
   │  │   每 100 条：W25_RefreshCounts() 实地对账              │
   │  ⑥ 有客户端时：ESP_SendFrame() → AT+CIPSEND 三步握手     │
   │                                                          │
   │  ⑦ 内层 200 × 10 ms 切片：                                │
   │       ESP_RxService()   ← 收上报 + 30 s 心跳（非阻塞）    │
   │       LED_Toggle()      ← 1 Hz / 4 Hz / 8 Hz             │
   │       BEEP On/Off       ← 报警时 200 ms 响 / 800 ms 停   │
   │       OLED_PageTime()   ← 时间画面每秒刷                  │
   │       Key_Scan()        ← 短按切画面/翻页，长按回画面 0    │
   └──────────────────────────────────────────────────────────┘
                                  │
         ┌────────────────────────┼────────────────────────┐
         ▼                        ▼                        ▼
   OLED（画面 0~4）        W25Q64（历史）         ESP-01S → 手机 TCP
```

**数据源单一性**：`g_temp_avg` / `g_humi_avg` 是显示、存储、推送、报警四处的**唯一**数据源。
这消除了一类难查的 bug ——"屏幕显示 30.1 但推送说 29.9"（如果各处各自换算就会发生）。

## 6. 模块接口总览

### 6.1 跨模块状态访问函数（约束 3 的产物）

驱动内部状态一律 `static`，只通过下列只读函数暴露：

| 原变量 | 访问函数 | 所属模块 |
|---|---|---|
| `g_ms_tick` | `BSP_Millis()` | `BSP/bsp_time.c` |
| `g_cpu_mhz` | `BSP_CpuMhz()` | `BSP/bsp_rcc.c` |
| `g_uart2_rx` / `g_uart2_rx_n` | `BSP_Uart2_RxBuf()`、`BSP_Uart2_RxAt()`、`BSP_Uart2_RxLen()` | `BSP/bsp_uart.c` |
| `g_uart2_scan` | `BSP_Uart2_ScanPos()`、`BSP_Uart2_ScanMove()`、`BSP_Uart2_RxReset()` | `BSP/bsp_uart.c` |
| `g_dht_raw` | `DHT_RawByte()` | `Drivers/dht11.c` |
| `g_dht_err` | `DHT_Error()` | `Drivers/dht11.c` |
| `g_dht_ok_cnt` / `g_dht_fail_cnt` | `DHT_OkCount()` / `DHT_FailCount()` | `Drivers/dht11.c` |
| `g_spi_ok` | `W25_IsOk()`（探测入口改为 `W25_Probe()`） | `Drivers/w25q64.c` |
| `g_oled_addr` | `OLED_Addr()` | `Drivers/ssd1306.c` |
| `g_rec_ok` / `g_rec_total` / `g_wr_sector` | `Hist_IsReady()` / `Hist_Count()` / `Hist_WrSector()` | `Drivers/hist_store.c` |
| `g_esp_ready` / `g_esp_link` / `g_esp_sent` | `ESP_IsReady()` / `ESP_IsLinked()` / `ESP_SentCount()` | `Drivers/esp8266_at.c` |

共 18 个只读接口。**写入一律只在模块内部发生**。

### 6.2 层间调用示例（一个完整请求的穿透路径）

以"OLED 显示一行温湿度"为例，看四层如何协作：

```
Core/ui_pages.c        调 OLED_ShowStr(0, 0, buf)
        │               ← 应用层决定"这一行显示什么"
        ▼
Drivers/ssd1306.c      拆成字符 → 取点阵 → 发给控制器
        │  调 OLED_ShowChar() → 取字库 font8x16.c
        │  调 I2C_WriteByte()  ← 器件层只说"写这个字节"
        ▼
BSP/bsp_soft_i2c.c     把字节变成 SCL/SDA 的电平翻转时序
        │  调 GPIOA_BSRR / GPIOB_BSRR  ← 只有这里认识寄存器
        ▼
硬件                   OLED 面板
```

`Util/fixed_str.c` 作为旁路被 `ui_pages.c`、`app.c`、`esp8266_at.c` 共用 —— 它不依赖任何硬件，因此是**跨层共享的纯工具**，这正是把它放在 `Util/` 的原因。

## 7. 可测试性设计

### 7.1 可测试性的唯一前提

**如果上层代码里出现寄存器地址，它就不可能在没有芯片的环境里编译。**

这就是约束 2（寄存器隔离）存在的根本理由 —— 它不是为了"代码整洁"，而是把"能在 PC 上跑的代码"与"必须靠硬件的代码"切开来。

### 7.2 边界怎么划：三个判断标准

| 标准 | 归入"可测" | 归入"不可测" |
|---|---|---|
| 输入输出是否只由参数决定 | 是（纯函数） | 否（依赖引脚状态、寄存器） |
| 是否需要精确时序 | 否 | 是（单总线、软件 I2C、SPI 位时序） |
| 失败是否只由算法决定 | 是（越界、溢出、取整方向） | 否（总线无应答、超时） |

### 7.3 三处为可测试性做的纯逻辑剥离

剥离原则：**逻辑一行不改，只换位置**。原调用点通过薄适配层接入，保持行为不变。

| # | 原位置 | 剥离出的内容 | 现在的位置 | 为什么这里能被测 |
|---|---|---|---|---|
| ① | `dht11.c` 校验和判定 + `Core/app.c` 温湿度换算 | 40 位帧 → 温湿度整数（含负温、×10 定点、校验和） | `Drivers/dht11_frame.c` | 输入是 5 字节数组，输出是整数，完全由参数决定 |
| ② | `hist_store.c` 的 `W25_RecRead` 排序寻址 | 逻辑序号 → Flash 绝对地址（双扇区乒乓的地址推算） | `Drivers/hist_index.c` | 纯算术：两个扇区条数 + 两个序号 → 一个地址 |
| ③ | `esp8266_at.c` 的 `static ESP_MatchAt` / `ESP_Has` | AT 应答关键词匹配 | `Drivers/esp_parse.c` | 输入是缓冲区 + 长度 + 关键词，输出是布尔 |

**③ 的一处实质改进**：原 `ESP_Has` 依赖缓冲区末尾的 `'\0'` 来界定搜索范围。但 USART2 是定长缓冲、可能刚好被填满而没有结束符。新接口把长度显式传入：

```c
uint8_t ESP_FindToken(const char *buf, uint16_t len, const char *token);
uint8_t ESP_MatchAtIn(const char *buf, uint16_t len, uint16_t pos, const char *token);
```

并专门写了一条**用不含 `'\0'` 的定长数组**去撞它的测试用例 —— 这是"为可测性重构"顺带修掉真实隐患的例子。

### 7.4 用构建配置再守一遍分层

```make
TEST_CFLAGS := -std=c11 -Wall -Wextra -O1 -g -IUtil -IDrivers -I$(TEST_DIR)
```

**只给 `-IUtil -IDrivers`，不给 `-IBSP`**。若被测代码哪天偷偷 `#include "bsp_gpio.h"`，这里会立刻编译失败。等于用构建配置第 3 次守住了分层边界，不需要额外写检查规则 —— **把约束编码进工具链，比写进文档可靠**。

### 7.5 剥离后的调用链（界面未变）

```c
/* Core/app.c —— 上层代码读起来更清晰了：取字节、解码、滤波 */
for (i = 0U; i < DHT_FRAME_LEN; i++) raw[i] = DHT_RawByte(i);
g_temp_now = DHT_DecodeTemp(raw);
g_humi_now = DHT_DecodeHumi(raw);
```

```c
/* Drivers/esp8266_at.c —— 适配层：把 BSP 的缓冲喂给纯函数，调用点一行未改 */
static uint8_t ESP_Has(const char *t)
{
    return ESP_FindToken(BSP_Uart2_RxBuf(), BSP_Uart2_RxLen(), t);
}
```

## 8. 演进路径

架构的价值在于**它让某些改动变便宜**。下面是几类预期改动具体要动哪里：

| 预期改动 | 需要改的文件 | 不需要改的 | 为什么便宜 |
|---|---|---|---|
| **换同系列芯片**（F103C8 → F103RB） | `STM32F103C8TX_FLASH.ld`（容量） | 全部 `.c` | 寄存器与引脚兼容 |
| **换到 F4 / GD32 等其他系列** | 整个 `BSP/`（寄存器地址、时钟树配置） | `Core/`、`Drivers/` 的业务逻辑、`Util/` | 器件驱动只依赖 BSP 提供的接口（如 `OW_WaitLevel()`、`I2C_WriteByte()`），不依赖寄存器 |
| **换 OLED 型号**（SSD1306 → SH1106） | `Drivers/ssd1306.c`（初始化序列、列偏移） | 其余全部 | `Core/ui_pages.c` 只调 `OLED_ShowStr(page, col, str)` |
| **换温湿度传感器**（DHT11 → SHT30，I2C 接口） | 新增 `Drivers/sht30.c`，改 `Core/app.c` 的调用点 | `Util/filter.c`、`Core/ui_pages.c`、`hist_store.c`、`esp8266_at.c` | 上层拿到的仍是 ×10 定点整数，数据模型不变 |
| **加 RS485 + Modbus RTU**（工业现场最对口） | 新增 `BSP/bsp_rs485.c`（方向控制引脚、收发切换）、`Drivers/modbus_rtu.c`（帧格式、CRC、寄存器映射）、`Core/` 里新增从站任务 | `Drivers/` 现有器件驱动、`Util/` | 协议栈是纯增量；CRC 与帧解析可以按 `Util/` 的规格写成**可在 PC 上单测的纯函数** |
| **加参数掉电保存 + 双备份 CRC** | 新增 `Drivers/param_store.c`（复用 W25Q64 或另开扇区） | 现有记录系统 | 存储驱动已具备"扇区头 + 魔数 + 序号对账"的可复用模式 |
| **加 IWDG 看门狗** | `BSP/` 新增初始化 + 主循环喂狗点 | 其余全部 | 主循环已有明确的心跳位置（10 ms 切片循环内） |
| **接入 RTOS** | `Core/` 调度改为任务；`app.h` 中共享变量需改为访问器 + 互斥 | `Drivers/`、`BSP/`、`Util/` | 驱动层没有全局可变状态暴露在外（约束 3 的产物），改造成本被限制在 `Core/` |

> **注意最后一行**：约束 3 让"将来接 RTOS"这件事的成本被限制在应用层。这不是巧合 ——
> 接口收敛的一个直接后果就是**并发改造的影响面可控**。

## 9. 架构约束的边界（诚实说明）

架构不解决所有问题，以下是明确的局限：

| 局限 | 说明 | 若要解决 |
|---|---|---|
| **时序正确性无法用单测覆盖** | 单总线、软件 I2C、SPI 位时序只能在实机上验证 | 需要示波器 + 逻辑分析仪；或用 GPIO 翻转 + 定时器捕获做自检 |
| **中断并发只有人工审查** | 接收中断与主循环对缓冲的并发访问靠"清缓冲时关中断"这一约定 | 需要静态分析工具或形式化方法 |
| **掉电一致性未做实测验证** | 乒乓设计的正确性来自推理，未做"写入过程中切断电源"的重复试验 | 需要一个可控电源开关与自动化脚本 |
| **跨层数据依赖仍存在** | `Core/app.c` 依赖 `dht11.h` 提供的 `DHT_RawByte()`，若 DHT11 被换掉，`Core/` 需要改 | 可加一层"传感器抽象接口"（函数指针表）；但当前只有一个传感器，抽象是负收益 |
| **CubeIDE 工程与 Makefile 需手工同步** | 新增源文件时两处都要登记 | 可由 CubeIDE 工程文件自动生成 Makefile 源列表，或反过来 |
