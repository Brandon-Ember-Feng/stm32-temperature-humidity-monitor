# 复盘 08 · 烧录成功但串口一条数据都没有

| 项 | 内容 |
|---|---|
| 发生时间 | 2026-10（四层重构后的首次烧录） |
| 影响范围 | 无法确认固件是否在运行 |
| 严重度 | 中（阻塞验证，但不损坏任何东西） |
| 定位耗时 | 约 30 分钟 |
| 类别 | 工具链行为 |

---

## 现象

用 `STM32_Programmer_CLI` 烧录，输出显示**成功**：

```
Memory programming ...
Download verified successfully
```

随即打开串口监听 —— **收到 0 字节**。一条自检日志都没有。

而板载 LED 是正常闪的（说明程序确实在跑）。

---

## 定位过程

### 第 1 步：区分"没在运行"与"在运行但没输出"

LED 在正常闪 ⇒ **程序在跑、时钟配置正确、主循环在转**。
串口 0 字节 ⇒ 问题在**输出链路**（USART1 配置、CH340 接线、或…）。

但这里有个矛盾：**如果 LED 在闪，说明 `main()` 里的 LED 长亮 1.5 s 已经走过，那之后紧接着就是 `UART_Puts()`** —— 应该立刻有输出才对。

### 第 2 步：直接测串口链路（排除 CH340）

用最短路径验证：在 `main()` 最开头加一句 `UART_Puts("HELLO\r\n")`，重新烧录。

**仍然 0 字节。**

⇒ 但这还不能说明 USART1 配错了（因为 `main()` 最开头那次调用发生在 `Clock_Init()` 之前，波特率算不出正确值 —— 这个实验设计本身有问题）。

### 第 3 步：回到"烧录"这一步看细节

怀疑点转移：**烧录结束之后，芯片处于什么状态？**

查 `STM32_Programmer_CLI` 的行为：

```
-c "port=SWD mode=UR reset=HWrst freq=1000"   ← 我们用的
```

- `mode=UR` = **connect Under Reset**：连接时先按住复位
- 烧录完成、CLI 退出时 —— **芯片停在 halt 状态**（调试器未 resume）

⇒ **CPU 是停住的**。那 LED 为什么在闪？—— 因为闪烁发生在**上一次烧录之前**的旧程序运行期间；观测时的"LED 在闪"是视觉惯性判断，实际上电后 LED 是长亮不动的。

（这一步的关键是：**回头质疑了自己"LED 在闪"这个前提**。）

### 第 4 步：验证"halt 假设"——补一条复位命令

```bash
# 只补一条连接 + 复位命令，不烧录
STM32_Programmer_CLI.exe -c "port=SWD mode=UR reset=HWrst freq=1000"
```

再监听串口：

```
=== 温湿度监测仪 v1.2（DHT11 + OLED + W25Q64 + 蜂鸣器 + ESP8266 WiFi）===
[自检] 蜂鸣器短鸣 200ms（配置为低电平触发）：...
[SDA自检] 通过（线上有上拉，接线正常）
[I2C总线] 空闲电平 SCL(PB6)=1 SDA(PB7)=1
[I2C总线] 扫描到 1 个器件: 0x78
[W25Q64] JEDEC ID = 0xEF4017
...
```

**收到 413 字节。**

⇒ **假设成立，根因确认。**

### 第 5 步（顺带发现）：`mode=hotplug` 无法擦除

排查过程中还试过默认的 `mode=hotplug`（不停 CPU，直接读寄存器 —— 对在线诊断很友好）：

```
failed to erase memory
```

⇒ **hotplug 模式下无法擦除 Flash**，所以不能用它烧录。
它的正确用途是：**读寄存器/读内存做在线诊断**（退出时自动 resume，不会把芯片留在 halt）。

---

## 根因

**`STM32_Programmer_CLI` 烧录完成后，芯片停在 halt 状态，CPU 不执行代码，因此串口没有任何输出。**

现象之所以有迷惑性，是因为"烧录成功"的输出**只说明 Flash 里的内容正确**，不说明 **CPU 在运行** —— 这是两件事。

---

## 修复与验证

### 修复：烧录后必须再显式复位一次

```bash
# 烧录
STM32_Programmer_CLI.exe -c "port=SWD mode=UR reset=HWrst freq=1000" \
                         -w build/temp-monitor.hex -v

# ★ 再补一条：只连接 + 复位，不烧录
STM32_Programmer_CLI.exe -c "port=SWD mode=UR reset=HWrst freq=1000"
```

这条已经被写进 `Makefile` 的 `flash` 目标，**不需要每次手工敲**：

```make
flash: all
	@echo ">> 烧录 $(BUILD_DIR)/$(TARGET).hex"
	$(PROGRAMMER) -c "port=SWD mode=UR reset=HWrst freq=1000" \
	              -w $(BUILD_DIR)/$(TARGET).hex -v
	@echo ">> 烧录后再显式复位一次（否则芯片停在 halt，串口一条数据都没有）"
	$(PROGRAMMER) -c "port=SWD mode=UR reset=HWrst freq=1000"
```

### 两条工具使用约定（已固化）

| # | 约定 | 说明 |
|---|---|---|
| 1 | **烧录必须用 `mode=UR`（under reset）** | `mode=hotplug` 无法擦除 Flash，会报 `failed to erase memory` |
| 2 | **烧录后必须再显式复位一次** | 否则芯片停在 halt，串口 0 字节。实测：直接监听 0 字节；补复位 413 字节 |

补充一条：**`mode=hotplug` 读寄存器是安全的**（退出自动 resume），适合做在线诊断。
详见 `docs/postmortem/` 与本项目 SWD 诊断手法（读 RAM 变量、模拟按键）。

### 验证

| 项 | 结果 |
|---|---|
| 烧录后直接监听串口 | 0 字节（复现） ✔ |
| 补一条复位命令后监听 | 413 字节自检日志 ✔ |
| `make flash` 一次完成 | 烧录 + 复位，串口立即可用 ✔ |
| `mode=hotplug` 尝试烧录 | `failed to erase memory`（复现） ✔ |

### 顺带固化的三条接线约定（SWD）

1. 烧录器只接 **`SWDIO` / `SWCLK` / `GND`** 三根线
2. **不要同时接 3.3 V** —— 避免两个电源并联
3. **`PA13` / `PA14` 保留给 SWD，不得挪作他用**

## 可迁移的教训

1. **"写入成功"不等于"程序在运行"**。
   Flash 校验通过只证明存储内容正确；CPU 是否执行、时钟是否配置正确、是否停在 halt，都是独立的事。
   **任何"成功"提示都要问一句：它到底证明了什么？**
2. **观测到的现象可能是"残留"而不是"当前"**。
   "LED 在闪"这个前提实际上是错的 —— 遇到矛盾（LED 闪但串口无输出）时，**先质疑观测本身**，而不是急着解释矛盾。
3. **工具的行为要显式验证一次，然后固化成脚本**。
   这次手动确认了"需要补复位"之后，立刻把它写进 `Makefile` —— 否则下次接手的人（半年后的自己）会重复踩一遍。
4. **同一个工具的不同模式，能力边界不同**：
   `mode=UR` 能擦能写但会把 CPU 留在 halt；`mode=hotplug` 不能擦写但能安全读寄存器。
   **知道每个模式的适用场景，比记住"哪个能用"更有价值。**
5. **把结论写进"用户能看到的地方"**：`Makefile` 的注释、README 的烧录章节、故障速查表。
   写在提交信息里等于没写。
