# 复盘 07 · 极值画面恒显示 3276.7 / −3276.8

| 项 | 内容 |
|---|---|
| 发生时间 | 2026-10-06（四层重构的等价性校验阶段） |
| 影响范围 | "历史极值统计"功能**从未真正实现**，但一直"看起来在显示数字" |
| 严重度 | **高（功能完全不可用，且伪装成正常）** |
| 类别 | 逻辑缺陷 / 状态未初始化 |

> **这是本项目最值得记录的一次缺陷**：它没有让任何代码报错、没有让任何测试失败、
> 没有让屏幕出现乱码 —— 它只是安静地显示一个"看起来像正常读数"的错误值。
> 如果不是做逐函数的等价性比对，这个 bug 会一直留在"已完成功能清单"里。

---

## 现象

切换到"极值"画面（画面 2），四条极值一直显示：

```
Tmax 3276.7
Tmin -3276.8
Hmax 3276.7
Hmin -3276.8
```

数值**上电后从不变化**，无论温度湿度怎么变（用手捂住传感器把温度拉高 5 °C，也纹丝不动）。

---

## 定位过程

### 第 1 步：先看这四个数字"长什么样"

关键观察：`3276.7` 和 `−3276.8` 不是随机的怪数，它们有明确的数学身份：

| 显示值 | ×10 后的整数值 | 十六进制 | 含义 |
|---|---|---|---|
| 3276.7 | 32767 | `0x7FFF` | **`int16_t` 的最大值** |
| −3276.8 | −32768 | `0x8000` | **`int16_t` 的最小值** |

⇒ 这不是"算错了"，而是 **"从来没被赋过值"**。因为 ×10 定点格式下，`int16_t` 的两个极端值恰好显示成 3276.7 / −3276.8。

**这一步是整次定位的转折点**：认出"极端值"就等价于认出"未初始化"。

### 第 2 步：验证这个假设

去 `Core/app.c` 看这 4 个变量的声明：

```c
int16_t  g_temp_min = 32767;
int16_t  g_temp_max = -32768;
int16_t  g_humi_min = 32767;
int16_t  g_humi_max = -32768;
```

初值确实是 `int16_t` 的两端 —— **这是设计上的正确做法**（第一次采样必定刷新它们，不需要额外的"是否第一次"标志位）。

那么问题只可能是：**刷新它们的代码不存在。**

搜全工程，看谁给这 4 个变量赋过值：

```bash
grep -rn "g_temp_max\s*=" --include=*.c .
```

**结果：只有声明处有 `=`，没有任何一处更新。**

⇒ 假设成立。

### 第 3 步：确认显示侧没问题

为了排除"是不是显示函数算错了"，检查 `ui_pages.c` 的极值画面：

```c
n = StrAppendStr(line, n, "Tmax ");
n = StrAppendFix1(line, n, g_temp_max);      /* 直接读变量 */
```

显示侧完全正确 —— 它忠实地把变量里的值显示出来了。**变量里装的是垃圾，不是显示错了**。

到这一步可以确定：**这是"功能没写"而不是"功能写错"。**

### 第 4 步：为什么这么久都没被发现？（元问题）

这一步比找到 bug 本身更重要。复盘原因：

| 原因 | 说明 |
|---|---|
| **数值看起来"像"正常读数** | 3276.7 会让人以为是"某个偏大的值"，而不是"非法值"。如果是 `0` 或 `-9999` 会更可疑 |
| **它"稳定"** | 上电后一直是这个数，不跳动。而"稳定"通常被解读为"工作正常" |
| **它"合理"地存在于屏幕的一角** | 极值画面不常看；即使看到，也不会立刻知道"正常应该显示什么" |
| **没有对照** | 没有"上电后极值应等于当前读数"这样的明确预期写下来 |
| **需求没被映射到验收项** | 需求写的是"记录开机以来的最大值与最小值"，但**没有对应的验收准则**（见下） |

**最后一条是根因的根因**：需求文档里 FR-06 当时的描述是"记录极值"，没有"验收准则"这一栏。没有验收准则的需求 = 无法判断是否完成。

---

## 根因

**`g_temp_min/max`、`g_humi_min/max` 四个变量只被声明和初始化，从未在任何地方被更新 —— 该功能实际未实现。**（FR-06）

深层原因是**需求缺少验收准则**：
- 需求只写了"记录开机以来的温度/湿度最大值与最小值"
- 但没有写"什么情况下算做到"（例如"上电第一次采样后，极值应等于当前滤波值"）

⇒ 于是"写了一个画面在显示这四个变量"就被当成了"功能完成"。

---

## 修复与验证

### 修复：在数据处理的必经路径上更新极值

```c
/* Core/app.c · DHT_Process() */

/* ---- 更新历史极值 ----
 * 【2026-10-06 修复】原 v1.2 只声明了这 4 个变量、从未赋值，
 * 导致「极值画面」恒显示 int16_t 的两个极端值（3276.7 / -3276.8）。
 * 用滤波后的值来比，免得单次跳变把极值带偏。 */
if (g_temp_avg > g_temp_max) g_temp_max = g_temp_avg;
if (g_temp_avg < g_temp_min) g_temp_min = g_temp_avg;
if (g_humi_avg > g_humi_max) g_humi_max = g_humi_avg;
if (g_humi_avg < g_humi_min) g_humi_min = g_humi_avg;
```

三点设计决定：

| 决定 | 理由 |
|---|---|
| 放在 `DHT_Process()` 里 | 这是每次采集的必经路径，不可能被绕过 |
| 用**滤波后**的值比较 | 单次跳变不应影响"历史极值"，否则极值会被噪声带偏 |
| 保留 `int16_t` 两端作为初值 | 第一次采样必定刷新它们，**不需要"是否第一次"标志位** —— 这是原设计中正确的部分，予以保留 |

### 验证

| 验证项 | 结果 |
|---|---|
| 上电首次采样后 | 四条极值 = 当前滤波值（不再是 3276.7） ✔ |
| 手捂传感器升温 | `Tmax` / `Hmax` 上升 ✔ |
| 移开手降温 | `Tmax` / `Hmax` **保持不回落**（极值的定义） ✔ |
| `Tmin` / `Hmin` | 只在新低出现时下降 ✔ |
| 长时间运行 | 极值单调不降（max）/ 不升（min） ✔ |

### 防复发：补上"验收准则"这一栏

这是本次缺陷最重要的产出。**把"需求"改写为"需求 + 可判定的验收准则"**：

| 需求 | 补充的验收准则 |
|---|---|
| FR-06 历史极值统计 | ① 上电第一次采样完成，4 个极值即等于当前滤波值<br>② 加热后最大值上升，回落时**不减小**<br>③ 极值用滤波值比较（不是原始值） |

并写进 `docs/design/01-需求规格说明书.md` 的 FR-06 条目，**连同缺陷记录一起**：

> 备注：该需求在 v1.2 首次实现时存在缺陷：4 个变量只声明未赋值，极值画面恒显示 int16 极端值（3276.7 / −3276.8）。已于 2026-10-06 修复，并作为回归测试项。

### 防复发：把"未初始化"变成可被机械发现的问题

这次是靠**人眼做逐函数比对**发现的。虽然这次抓住了，但依赖人的注意力。可以强化为：

- 所有"上电后应被立即刷新"的变量，初值取**明显不可能出现的值**（本例的 `int16_t` 两端恰好满足这个条件 —— 这也是它能被认出来的原因）
- 新功能必须同时写"验收准则"，准则要能回答"如果这个功能完全没实现，屏幕上会看到什么"（这是个非常有效的检测问句）

## 可迁移的教训

1. **认出"极端值"就等于认出"未初始化"**。
   看到 `32767` / `−32768` / `65535` / `0xFFFFFFFF` / `NaN` 这类数，**第一个假设就应该是"没赋过值"**，而不是"算错了"。
2. **"稳定不动的数字"是可疑信号**，不是"工作正常"的证据。
   一个应该随输入变化的量如果纹丝不动，先怀疑它根本没被更新。
3. **"看起来像正常值"的错误最危险**。
   全 `0xFF` 一眼就知道是错的；`3276.7` 看起来只是个偏大的读数。**设计初值时要有意让它"一眼可辨"**（本例的 `int16_t` 两端恰好做到了）。
4. **需求必须有可判定的验收准则**。
   "记录开机以来的最大值与最小值"无法判定；"上电第一次采样后极值应等于当前值"可以判定。
   没有验收准则的需求，实现者很容易把"写了个画面显示它"当成完成。
5. **"功能没写"和"功能写错"要用不同手段发现**：
   - 写错 ⇒ 单元测试、边界用例能抓
   - 没写 ⇒ 单元测试抓不到（没有代码可测），只能靠**逐项对照需求清单**或**逐函数等价性比对**
6. **重构的等价性校验不只是"防改坏"，它同时是一次全量审计**。
   这次缺陷是在"逐函数比对重构前后是否一致"的过程中发现的 —— 比对迫使你把每个函数都看一遍，
   而"看一遍"正是发现"这里缺了什么"的唯一途径。**这是重构的一项额外收益。**
