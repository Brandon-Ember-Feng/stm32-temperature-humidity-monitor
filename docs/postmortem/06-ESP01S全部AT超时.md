# 复盘 06 · ESP-01S 全部 AT 指令超时

| 项 | 内容 |
|---|---|
| 发生时间 | 2026-09-21 |
| 影响范围 | 无线推送完全不可用 |
| 严重度 | 高（功能阻断） |
| 定位耗时 | 约 4 小时（跨越多种现象） |
| 类别 | 供电 / 接线 / 模块固件行为 |

---

## 现象

三个**看起来像同一个问题、其实是三个不同原因**的现象，先后出现：

| # | 现象 | 发生频率 |
|---|---|---|
| A | 模块**毫无反应**，所有 AT 指令全部超时 | 初始，每次上电 |
| B | 模块能应答，但发送数据时永远回 `link is not valid` | 修好 A 之后 |
| C | 能正常推送一段时间，然后**突然连不上**（热点也消失） | 长跑时偶发 |

这正是一个需要警惕的信号：**不要找到第一个原因就停下。**

---

## 现象 A 的定位过程

### 第 1 步：确认不是"线接反"

ESP-01S 的 `TXD`/`RXD` 与 STM32 的 `PA3`/`PA2` 是**交叉**接的：

| 模块 | 方向 | 接到 |
|---|---|---|
| `TXD` | 模块输出 | `PA3`（USART2_RX） |
| `RXD` | 模块输入 | `PA2`（USART2_TX） |

已核对无误。**把线交换试过，也没反应** ⇒ 排除接反。

### 第 2 步：查 `CH_PD`

ESP-01S 是 2×4 共 8 针模块。除了 `VCC`/`GND`/`TXD`/`RXD`，还有一个 **`CH_PD`**（也叫 `EN`，Chip Power Down / 使能）。

**它必须接到 3.3 V，否则模块处于掉电/复位状态，毫无反应。**

实测：`CH_PD` 悬空 ⇒ 完全无应答。接上 3.3 V ⇒ **模块开始应答**。

⇒ **现象 A 的根因 #1：`CH_PD` 未接 3.3 V。**

### 第 3 步：查供电

`CH_PD` 接上后模块能应答了，但**不稳定** —— 偶尔又会没反应。

ESP-01S 的电流特性：

| 状态 | 电流 |
|---|---|
| 待机 | 约 70 mA |
| **发射瞬时峰值** | **300 mA+** |

而供电来源是 STM32 板载的 AMS1117（约 500~800 mA），看起来够 —— 但**面包板的接触电阻 + 杜邦线压降**在 300 mA 突变下会产生明显跌落。

实测到的关键症状：**CH340 突然从 Windows 设备列表里消失**。

这个症状非常有价值 —— 它说明**不是 ESP 的问题，是整个 3.3 V 轨被瞬时拉垮，把 CH340 一起带崩了**。USB 口的预算贴近 500 mA 上限。

⇒ **现象 A 的根因 #2：供电不足 / 电源轨跌落。**

### 第 4 步：三条供电红线

排查后固化下来：

| # | 红线 | 原因 |
|---|---|---|
| 1 | **`VCC` 绝不接 5 V** | ESP-01S 不是 5 V 容忍器件，立刻烧毁 |
| 2 | **`CH_PD` 必须接 3.3 V** | 不接则毫无反应 |
| 3 | **面包板正极轨只能有一个电源** | STM32 的 3.3 V；ST-Link 只接 `SWDIO`/`SWCLK`/`GND`，**不要接 3.3 V**（两个电源并联） |

外加两条实践建议：

- **470 µF 电解电容必须插在离 ESP 最近的孔**（远一点就起不到瞬时补偿作用）
- **不要用 ST-Link 的 3.3 V 给 ESP 供电**（仅约 100 mA，会反复重启）

> 还要注意：**很多面包板的"正极轨"在中间是断开的**。跨在断口两侧的两个器件，看着都在"正极轨"上，其实是两个独立的网络 —— 等于没供电。

## 现象 B 的定位过程

模块能应答之后，初始化序列跑通了，但每帧数据发送都失败。

### 第 1 步：看模块到底回了什么

把回显打出来（`ESP_LOG_FRAMES = 1`）：

```
[ESP>] AT+CIPSEND=0,34
[ESP<] link is not valid
```

### 第 2 步：查模块的连接状态

发 `AT+CIPSTATUS` —— 回：

```
STATUS:5
```

`STATUS:5` 在 ESP8266 的语义里是"已获得 IP、可以通信" ⇒ **看起来一切正常，但实际发不出去。**

### 第 3 步：定位到"僵尸链路"

回想场景：**模块在 STM32 上电之前就已经建立过 TCP 连接，而那条连接被对端粗暴掐断（RST）。**

模块内部因此留下一条"僵尸链路"：

- `AT+CIPSTATUS` 照样报 `STATUS:5`（因为它认为自己在多连接模式下有活动链路）
- 但 0 号链路实际已死 ⇒ 所有 `AT+CIPSEND=0` 都回 `link is not valid`

⇒ **现象 B 的根因：模块内部残留的僵尸链路。**

`AT+CIPCLOSE=0` 可以清掉它。注意：**没有链路时这条指令回 `UNLINK` + `ERROR`，属正常提示**，所以只看不断言。

### 修复

在初始化序列末尾固定加一条清理（不判断结果）：

```c
/* ③ 清掉可能残留的 0 号链路。
 *    为什么需要：如果模块在 STM32 上电前就已经建过连接、而那条连接被对端
 *    粗暴掐断（RST），模块内部会留下一条"僵尸链路"——此后所有
 *    AT+CIPSEND=0 都回 `link is not valid`，而且 AT+CIPSTATUS 照样报
 *    STATUS:5 看着像连着。2026-09-21 实测踩到过这个坑。
 *    没有链路时这条指令回 `UNLINK` + `ERROR`，属正常提示，所以只看不断言。 */
(void)ESP_Cmd("AT+CIPCLOSE=0", "OK", 1500U, 1U);
```

### 配套：运行期也要能补判

初始化清一次不够 —— 运行期也可能出现"模块没上报 CLOSED、但已经发不出去"。所以在发送失败分支里补判：

```c
if (!ESP_WaitFor(">", ESP_PROMPT_MS))
{
    g_esp_fail++;
    /* 模块没上报 CLOSED、但已经发不出去了 —— 靠这句错误文本补判 */
    if (ESP_Has("link is not valid"))
    {
        g_esp_link = 0U;
        UART_Puts("[ESP] 客户端其实已断开（link is not valid）\r\n");
    }
    return 0U;
}
```

清掉 `g_esp_link` 后，主循环下一轮就不再来打扰，避免每 2 秒白等 1 秒超时。

## 现象 C 的定位过程

长跑时偶发：突然连不上，热点也消失了。

### 第 1 步：判断"是谁的问题"

- 手机搜不到 `ESP_TEMP` 热点 ⇒ **模块侧的问题，不是 STM32 侧**
- STM32 日志显示一切正常 ⇒ **STM32 完全不知道模块出事了**

### 第 2 步：链接到现象 A 的根因 #2

供电瞬时跌落 ⇒ **模块自己复位**。复位后：

- 热点丢失
- TCP 服务器丢失
- 之前建立的连接全部消失
- **而 STM32 侧的 `g_esp_ready` 仍然是 1** ⇒ 代码看起来一切正常，用户那边却是"怎么突然连不上了"

⇒ **现象 C 的根因：模块自发复位，而主机无感知。**

### 修复：30 秒心跳 + 自动恢复

```c
void ESP_KeepAlive(void)
{
    if ((BSP_Millis() - g_esp_last_ka) < ESP_KA_MS) return;   /* 30 秒一次 */
    g_esp_last_ka = BSP_Millis();

    if (!ESP_Cmd("AT", "OK", 500U, 0U))
    {
        UART_Puts("[ESP] 模块无应答（很可能复位了），重新初始化...\r\n");
        g_esp_ready = 0U;
        g_esp_link  = 0U;
        delay_ms(500U);

        if (ESP_Setup()) UART_Puts("[ESP] 已恢复：热点重新建立\r\n");
        else             UART_Puts("[ESP] 恢复失败，30 秒后再试\r\n");
    }
    else if (g_esp_link == 0U)
    {
        UART_Puts("[ESP] 心跳正常，等待手机连接（SSID " ESP_AP_SSID "）\r\n");
    }
}
```

心跳**不依赖"模块有没有报错"**，而是主动去问 —— 这样即使模块悄悄复位（没有任何上报），也能被发现。

## 根因汇总

| 现象 | 根因 | 类别 |
|---|---|---|
| A | `CH_PD` 未接 3.3 V（完全不工作） | 接线 |
| A | 供电不足 / 电源轨瞬时跌落（不稳定） | 供电 |
| B | 模块内部残留僵尸链路（`STATUS:5` 但发不出去） | 模块固件行为 |
| C | 模块自发复位，主机无感知 | 缺少故障检测 |

**四个独立原因，两个现象（A/B/C 中的 A 其实含两条）。** 这也是本次复盘最大的教训：**同一个症状可以由多个不相关的原因叠加造成**。

## 验证

| 验证项 | 结果 |
|---|---|
| 200 次连续 AT 压测 | 全部成功，模块零重启 ✔ |
| 稳定推送 | 手机端连续接收约 200 帧无中断 ✔ |
| `>` 提示符时延 | 208~219 ms（12 次采样，抖动 11 ms） ✔ |
| 拔掉热点后恢复 | 30 秒内心跳检测到并重建热点 ✔ |
| `CH_PD` 悬空复现 | 完全无应答（确认根因 A-1） ✔ |

## 可迁移的教训

1. **"没有反应"和"有反应但不对"是两类问题**，要分开排查。
   前者查使能/供电（`CH_PD`、VCC），后者查协议/状态（僵尸链路）。
2. **同一个症状可能有多个叠加原因**。
   每修好一个就重新完整验证一遍，不要假设"找到原因了，剩下的问题自然是同一个"。
3. **外设的"状态查询"可能说谎**。
   `AT+CIPSTATUS` 报 `STATUS:5` 而实际发不出去 —— **不要把"状态查询通过"当成"功能可用"**。
   可靠的判据是**主动做一次真实操作**（发一帧看有没有 `SEND OK`），而不是读状态。
4. **模块可能悄悄复位，主机必须主动检测**。
   凡是"有自己的 CPU"的外设（WiFi 模块、传感器模块、驱动器），都要假设它会自己重启 —— 心跳是标准解法。
5. **供电问题是嵌入式里最容易被误判为软件问题的故障**。
   判据：**其他设备也一起异常**（这里是 CH340 从设备列表消失）⇒ 一定是电源，不是代码。
6. **把"必须遵守的接线红线"单独列出来**（`CH_PD` 必须拉高、VCC 绝不接 5 V）。
   这类约束与具体代码无关，写进代码注释 + README + 接线表三处。
