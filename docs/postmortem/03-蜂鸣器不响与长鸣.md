# 复盘 03 · 蜂鸣器不响 / 上电一直长鸣

| 项 | 内容 |
|---|---|
| 发生时间 | 2026-09（v1.2 开发期） |
| 影响范围 | 声音报警不可用；接线文档返工 |
| 严重度 | 中 |
| 定位耗时 | 约 1.5 小时（含文档返工） |
| 类别 | 硬件形态认知 |

---

## 现象

分两个阶段：

**阶段一 · 完全没声**

按"2 针裸蜂鸣器"的思路接好后上电，蜂鸣器**完全不响**。用万用表量 IO 脚电平确实在变化（软件在输出），但就是没声音。

**阶段二 · 一直长鸣**

调整接线后变成另一个极端：上电就一直响，不会停。而需求是"只在超阈值时断续响"。

---

## 定位过程

### 第 1 步：先确认软件真的在输出

用串口打印 + 万用表量 `PB5` 电平：

| 时刻 | `PB5` 实测 |
|---|---|
| `BEEP_On()` 期间 | 低电平 |
| `BEEP_Off()` 期间 | 高电平 |

⇒ **软件侧完全正常**，问题在"这个电平送到蜂鸣器上为什么不出声/一直出声"。

### 第 2 步：查蜂鸣器到底是什么形态

翻出实物核对 —— 手上这个是**3 针模块**，丝印 `VCC / IO / GND`（不是 2 针裸蜂鸣器）。

这是定性错误的起点：**2 针裸蜂鸣器和 3 针模块的驱动方式完全不同**。

| 形态 | 接法 | 驱动 | 电流 |
|---|---|---|---|
| **2 针裸蜂鸣器** | 一端 VCC、一端 IO | 需自行串限流电阻、考虑灌/拉电流能力 | 由 IO 直接承担（可能超 STM32 的 20 mA） |
| **3 针模块**（本项目） | VCC / GND / IO(信号) | **模块自带三极管驱动级**，IO 只认逻辑电平 | IO **不消耗**引脚电流，由 VCC 供电 |

⇒ 之前按 2 针写的接线文档、以及"要不要串电阻""用灌电流还是拉电流"这些讨论，**全部作废**。

### 第 3 步：确认"有源"还是"无源"

| 类型 | 驱动方式 |
|---|---|
| **有源** | 给电就响，内部自带振荡电路，**不需要 PWM 方波** |
| **无源** | 必须用方波驱动（例如 2 kHz）才会响 |

本项目模块是**有源**的 ⇒ 直接给固定电平即可，不需要定时器输出 PWM。这也解释了"为什么没有用 PWM 也能响"。

### 第 4 步：确认触发极性（阶段二的原因）

模块丝印上写着「**低电触发**」（`IO = 0` 响，`IO = 1` 静音）。

而第一版固件是按"高电平触发"写的：

```c
#if BEEP_ACTIVE_HIGH
    #define BEEP_On()   ...
#endif
```

⇒ 上电时 IO 默认高 ⇒ **一直响**。这就是阶段二的根因。

### 第 5 步：为什么阶段一是"完全没声"

阶段一的问题更简单：**接线时把 `VCC` 和 `GND` 接反了**。

3 针模块电源反接通常**不会烧毁**，而是"不烧不响"的静默失效 —— 这个现象极具迷惑性，看起来完全像软件故障。

---

## 根因

三重因素叠加，且**每一重都源于"没有先确认硬件形态就写代码/写文档"**：

| # | 根因 | 表现 |
|---|---|---|
| 1 | 按"2 针裸蜂鸣器"的假设设计，实际是 **3 针模块** | 驱动方案错误 |
| 2 | **`VCC` / `GND` 接反** | 静默失效：不响 |
| 3 | **触发极性与模块不匹配**（固件按高触发，模块是低触发） | 反面失效：一直响 |

---

## 修复与验证

### 修复

**接线**：按丝印 `VCC / IO / GND` 接 —— `VCC → 3.3 V`、`GND → GND`、`IO → PB5`。

**固件**：把极性做成可配置宏，默认按本模块的"低电平触发"：

```c
/* Drivers/beep.h */
#define BEEP_ACTIVE_HIGH  0U    /* 0 = 低电平触发（本模块），1 = 高电平触发 */
```

### 关键改进：加"上电短鸣 200 ms"自检

极性对不对，如果等温度升到 30 °C 触发报警才知道，可能要等半小时。**上电短鸣一下，5 秒内就能定案**：

```c
BEEP_On();
delay_ms(200U);
BEEP_Off();
UART_Puts("[自检] 蜂鸣器短鸣 200ms（配置为");
UART_Puts(BEEP_TRIG_TXT);
UART_Puts("）：若此后一直长鸣不停，说明模块是另一种触发极性\r\n");
```

判据表（写进 README 和代码注释）：

| 现象 | 结论 | 动作 |
|---|---|---|
| 短鸣后安静 | 极性与接线都正确 | 无需处理 |
| **一直长鸣** | 极性反了 | 把 `BEEP_ACTIVE_HIGH` 改成 `1` 重烧 |
| **完全没声** | 查 `VCC`/`GND` 是否接反、是否真的量到 3.3 V | 重新接线 |

并且把当前极性同时输出到 **OLED 第 4 行**（`BEEP_TRIG_STR`）—— 没接串口也能看到配置值。

### 验证

| 项 | 结果 |
|---|---|
| 上电 | 短鸣 200 ms 后安静 ✔ |
| 报警时（手捂传感器超 30 °C） | 响 200 ms / 停 800 ms 断续鸣响 ✔ |
| 非报警状态 | 静音 ✔ |

### 文档返工

这次故障的**连带成本**是接线文档全部重写：原来按 2 针写的"要不要串限流电阻""灌电流/拉电流"等内容全部删除，改为 3 针模块的描述。

> 这个代价比定位本身大得多 —— 也是"先确认硬件形态"这条规则的直接来源。

---

## 可迁移的教训

1. **"蜂鸣器"不是一个确定的东西**。它至少有 6 种组合：2 针/3 针 × 有源/无源 × 高触发/低触发。
   **任何写代码前都要先问清形态**，否则返工成本远大于确认成本。
2. **电源反接的典型症状是"静默失效"**：不烧、不响、看起来像软件问题。
   所以"量一下 VCC 是不是真的 3.3 V"应该排在任何软件排查之前。
3. **极性这类"一次性配置"，要用上电自检把判定时间从半小时压到 5 秒**。
   自检的价值不在于"发现问题"，而在于**把发现问题的等待时间降下来**。
4. **配置项要能自己说明自己**：把当前的极性配置同时打到串口和 OLED，排查时不用回去翻代码。
5. **这类"形态认知错误"会污染文档**，而不只是污染代码。写硬件相关文档时，第一句话应该是"实物是什么型号/丝印是什么"，而不是从功能出发描述。
