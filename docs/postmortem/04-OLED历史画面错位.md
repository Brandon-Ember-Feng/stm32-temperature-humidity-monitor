# 复盘 04 · OLED 历史画面文字错乱（含一行完全不显示）

| 项 | 内容 |
|---|---|
| 发生时间 | 2026-09（v1.2 开发期） |
| 影响范围 | 历史记录画面完全不可读 |
| 严重度 | 中 |
| 定位耗时 | 约 1 小时 |
| 类别 | 显示 / 静默失败 |

---

## 现象

历史画面（`g_mode == 3`）显示效果分两种，都很怪：

**症状 A · 文字互相压叠**

标题被数据压住下半截，各条记录上下错开 8 像素、彼此重叠 —— 整页糊成一团。

**症状 B · 第 4 条一个字都不显示**

按"每页 4 条"设计时，**第 4 条记录在屏幕上完全不存在**。不是显示成乱码，是**整行一个字都没有**。

其余画面（温湿度 / 时间 / 极值 / WiFi）显示完全正常。

---

## 定位过程

### 第 1 步：既然其他画面正常，问题不在 I2C / 初始化

温湿度画面显示正常 ⇒ OLED 通信、供电、`OLED_Init`、字库都没问题。

⇒ 问题被限定在**历史画面这一处的排版代码**上。

### 第 2 步：看"第 4 条整行不显示"这个线索

**整行不显示**比"显示成乱码"更有指向性：乱码是数据问题，整行空白是**写显存的调用根本没发生**。

去看被调用的绘制函数：

```c
void OLED_ShowChar(uint8_t page, uint8_t col, char ch)
{
    if (page > 6U || col > 120U) return;      /* ★ 保护：超出行范围直接返回 */
    ...
}
```

⇒ **`page > 6` 时静默 return，不画任何东西、不报错。**

### 第 3 步：算一下屏幕到底有几行

看 SSD1306 的显存结构：128×64，纵向 64 像素被切成 **8 个 page**，每 page 8 像素。

字库是 **8×16** 点阵 ⇒ **一个字符要占两个 page**（上半 + 下半）。

```
page 0 ┐
page 1 ┘  ← 第 1 行（page 0 是上半，page 1 是下半）
page 2 ┐
page 3 ┘  ← 第 2 行
page 4 ┐
page 5 ┘  ← 第 3 行
page 6 ┐
page 7 ┘  ← 第 4 行
```

⇒ **合法的行起始 page 只有 `0 / 2 / 4 / 6`。**

### 第 4 步：看原代码用了哪些 page

按"每页 4 条 + 1 行标题"的设计，原代码从 `page 1` 起排数据行：

| 用途 | 原 page | 问题 |
|---|---|---|
| 标题 | 0 | ✔ |
| 第 1 条 | **1** | ✗ `1 = 0 + 1` ⇒ 落在标题行的**下半截**，把标题压掉一半 |
| 第 2 条 | **3** | ✗ `3 = 2 + 1` ⇒ 压住第 2 行的下半截 |
| 第 3 条 | **5** | ✗ 同上 |
| 第 4 条 | **7** | ✗ `7 > 6` ⇒ 被 `OLED_ShowChar` 的保护**整行拦掉** |

⇒ **一个错误（从 page 1 起排、每行 +2 而不是 +2 的整数倍）同时解释了两个症状：**
- 起始 page 是奇数 ⇒ 每个字符都跨在两行之间 ⇒ **症状 A（压叠）**
- 第 4 条落在 page 7 ⇒ 被保护拦掉 ⇒ **症状 B（整行空白）**

**根因确认。** ——这里也解释了一个看似矛盾的现象：为什么"每页 4 条"比"每页 3 条"看起来更合理，却完全不能工作。因为 **4 条数据 + 1 行标题 = 5 行 > 屏幕的 4 行**，物理上放不下。

---

## 根因

**没有意识到 8×16 字库下屏幕只有 4 行（page `0/2/4/6`），把"每字符占 2 个 page"的换算写成了"行号 +1"。**

正确的换算是：

```c
row_page = HIST_ROW_TOP + row * 2U;      /* +2，因为一个字符占 2 个 page */
```

而不是：

```c
row_page = HIST_ROW_TOP + row;           /* +1 —— 错误：每行会跨在两条字符行的中间 */
```

---

## 修复与验证

### 修复 1：每页改为 3 条，行距按 +2

```c
/* Core/ui_pages.h */
#define HIST_PER_PAGE   3U    /* 每页 3 条（+1 行标题 = 4 行占满） */
#define HIST_ROW_TOP    2U    /* 第 1 条数据画在第 2 行，即 page 2   */
```

```c
/* Core/ui_pages.c */
uint8_t rpag = (uint8_t)(HIST_ROW_TOP + row * 2U);   /* row = 0,1,2 → page 2,4,6 */
OLED_ShowStr(rpag, 0, line);
```

标题占 page 0，三条数据占 page 2 / 4 / 6 —— 整整 4 行，刚好占满屏幕。

### 修复 2：把"踩过的坑"写进头文件注释

```c
/* 【为什么是 3 而不是 4 —— 这是踩过坑的数字】
 *   OLED 是 128x64，纵向 64 像素被切成 8 个 page（每 page 8 像素）。
 *   字库是 8x16 点阵，一个字符要占「上半 page + 下半 page」两格，
 *   所以整屏实际只有 4 行字符位置：page 0 / 2 / 4 / 6。
 *   历史画面需要 1 行标题，剩下的 3 行才是数据。
 *   【曾经写成 4 条的后果】数据行从 page 1 起排（1/3/5/7）：
 *   ① 第 1 条覆盖标题下半截；② 每条上下错开 8 像素、互相重叠；
 *   ③ 第 4 条落在 page 7，而 OLED_ShowChar 有 `page > 6 直接 return`
 *      的保护，整行一个字都不画。整页糊成一团。 */
```

### 修复 3：用"合法行号"约束新增画面

页脚显示 `M2/5` 之类信息时，固定使用 page 0 / 2 / 4 / 6 四个值。所有 `OLED_ShowStr` 的第一个参数只允许取这四个常量。

### 验证

| 项 | 结果 |
|---|---|
| 标题 | page 0，完整显示 ✔ |
| 3 条记录 | page 2 / 4 / 6，各占一整行、不重叠 ✔ |
| 4 行整体 | 上下对齐、无残影 ✔ |
| 翻页 | 每页 3 条，最后一页不足 3 条时该行显示空白（不显示垃圾内容） ✔ |

### 回归保护

`make check-layering` 管不到这类显示问题（它只管分层）。目前的保护手段是：
1. 头文件注释里写明踩坑记录
2. 常量 `HIST_PER_PAGE` / `HIST_ROW_TOP` 集中定义，不散落在代码里
3. README 与项目说明书的"常见故障速查"里列出"OLED 花屏/错位 → 行号只能用 0/2/4/6"

> **诚实说明**：目前**没有自动化测试**覆盖显示排版（需要像素级比对）。
> 现有的 `page > 6U` 保护只保证"不越界"，不保证"排得好看"。
> 这类问题的验证方式是"人工目视 + 用串口把当前页号/总页数打出来做对照"。

## 可迁移的教训

1. **"整行什么都不显示"是极强的线索**：它指向"函数根本没被调用"或"被提前 return 了"，
   而不是数据错误。**先去查有没有保护性 return**，这是最快的路径。
2. **静默失败（silent failure）比崩溃难查得多**。`if (page > 6U) return;` 是一道必要的保护，
   但它把"参数传错"变成了"什么都不发生" —— 代价是问题被推迟到很晚才被发现。
   **凡是这类"静默保护"，都要在文档和注释里写明它的存在**。
3. **换算错误往往是"差 2 倍"（这里是差 2 倍而不是差 1）**。
   当一个"行距"参数被写错时，优先确认**单位**：这里是"字符行"还是"page"？
   两者差 2 倍。单位混淆是最常见的换算 bug 来源。
4. **物理容量要先算清楚，再决定放几条**：`屏幕 4 行 − 标题 1 行 = 3 条数据`。
   反过来"先决定放 4 条、再看能不能排下"必然返工。
5. **踩过的坑要写进"下一个会改这里的人"能看到的地方** —— 头文件注释、常量定义旁边、
   故障速查表。写在提交信息里没用，因为改代码的人不会去翻历史提交。
