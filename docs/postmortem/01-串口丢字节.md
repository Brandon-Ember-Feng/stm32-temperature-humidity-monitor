# 复盘 01 · 串口 115200 下接收丢字节

| 项 | 内容 |
|---|---|
| 发生时间 | 2026-09-21 |
| 影响范围 | ESP-01S 全部 AT 指令超时，无线推送完全不可用 |
| 严重度 | 高（功能阻断） |
| 定位耗时 | 约 2 小时 |
| 类别 | 通信 / 中断 |

---

## 现象

ESP-01S 初始化时，四条 AT 指令（`ATE0` / `AT+CWMODE=2` / `AT+CWSAP` / `AT+CIPMUX=1`）**全部超时**。

串口日志看起来像这样（注意那个多余的空格）：

```
[ESP>] ATE0
[ESP<] (没等到期望应答) 
```

模块供电正常、`CH_PD` 已接 3.3 V、TXD/RXD 已交叉接线 —— 这些都已经确认过。

---

## 定位过程

### 第 1 步：先确认"模块到底回没回"

怀疑模块本身坏掉或接线有问题。但如果模块真的没回，日志里应该**一个字符都没有**。

关键观察：`(没等到期望应答)` 后面**多出一个空格**。

查打印函数 `ESP_LogResp()`：

```c
if ((c == '\r') || (c == '\n'))  UART_PutC(' ');   /* 换行 → 空格 */
```

⇒ **那个空格是一个 `\r` 变的。模块确实回了，只是回的内容被丢了。**

### 第 2 步：数一下应该收到几个字节

模块的应答是 `\r\nOK\r\n` —— 6 个字节。而我们只活下来 1 个。

差 5 个字节，说明**不是"收不到"，是"收到了但没接住"**。

### 第 3 步：查 STM32 侧怎么收的

当时的实现是**主循环轮询**：

```c
/* BSP_Uart2_RxPoll()：查询 RXNE 标志，有字节就搬走 */
while ((USART2_SR & (1U << 5)) != 0U) { ... }
```

调用时机：
- 正常主循环里，每 10 ms 一次
- AT 等待期间（`ESP_WaitFor`）最密也就每 1 ms 一次

### 第 4 步：算一下够不够快

| 参数 | 值 |
|---|---|
| 波特率 | 115200 |
| 一帧 | 起始位 + 8 数据位 + 停止位 = **10 位** |
| 一个字节的传输时间 | 10 / 115200 ≈ **87 µs** |

轮询周期 1 ms = **比字节间隔慢 11.5 倍**；主循环 10 ms 则慢 115 倍。

⇒ 到第 2 个字节到来时，第 1 个字节还躺在接收寄存器里没被读走。

### 第 5 步：验证硬件行为

查参考手册确认 STM32 的 USART 接收寄存器（DR）只有 **1 个字节**的容量，没有 FIFO：

- 新字节到来、旧字节未被读走 ⇒ 置 **ORE（溢出错误）** 标志，**并直接丢弃新字节**

⇒ 完美解释了"只活下来 1 个字节"这个现象：那 6 个字节里，只有第 1 个 `\r` 侥幸被读到，之后 5 个全部因溢出丢弃。而 `OK` 恰好在这 5 个之中，所以**每一条 AT 都凑不出 `OK`**。

---

## 根因

**用轮询方式接收 115200 的字节流，而轮询周期比字节间隔慢一个数量级以上。**

这是"设计假设错误"而不是"代码写错"：代码逻辑本身没问题（查标志、读 DR、清标志都对），错的是**用这种机制的时机**。

---

## 修复与验证

### 修复：改为接收中断

```c
USART2_CR1 = (1U << 13)      /* UE：串口使能 */
           | (1U << 3)       /* TE：发送使能 */
           | (1U << 2)       /* RE：接收使能 */
           | (1U << 5);      /* ★ RXNEIE：收到一个字节就中断 */

NVIC_ISER1 = (1U << 6);      /* USART2 中断号 38 → ISER1 bit 6 */
```

```c
void USART2_IRQHandler(void)
{
    /* 读 SR 再读 DR：这一对操作同时清掉 RXNE / ORE / NE / FE / PE */
    if ((USART2_SR & (1U << 5)) != 0U)
    {
        char c = (char)(USART2_DR & 0xFFU);
        if (g_uart2_rx_n < (BSP_UART2_RX_BUF - 1U))
        {
            g_uart2_rx[g_uart2_rx_n] = c;
            g_uart2_rx_n++;
        }
        else { /* 缓冲满：整体丢掉重来，比卡死好 */ }
    }
}
```

字节一进 DR 就在中断里被搬进缓冲，**中间没有间隙，一个都不丢**。

`BSP_Uart2_RxPoll()` 保留为"安全网"（万一字节在中断打开前就进了 DR），但不再是主路径。

### 连带修复：清缓冲必须关中断

```c
__asm volatile ("cpsid i" ::: "memory");
BSP_Uart2_RxReset();
__asm volatile ("cpsie i" ::: "memory");
```

否则接收中断可能正好插在清缓冲的几步之间，把新字节写进来，出现**"计数被清零、字节却已写入"**的错位。

### 验证

| 验证项 | 结果 |
|---|---|
| 四条 AT 指令 | 全部收到 `OK` |
| 200 次连续 `AT` 压测 | 全部成功，模块零重启 |
| `>` 提示符时延 | 208~219 ms（12 次采样，抖动 11 ms） |

### 回归保护

- 判断分层的规则 3（接口收敛）要求接收缓冲是 `static`，只能通过访问函数操作 ⇒ 减少了"别处直接改计数器"的可能
- `ESP_FindToken(buf, len, token)` 现在显式接收长度，**不依赖 `'\0'`**，把"缓冲被填满时越界读"这条另一类隐患也一起封住了

---

## 可迁移的教训

1. **"看起来什么都没有"和"有但只有一点点"是两种不同的故障**，要能区分。
   那个被转成空格的 `\r` 就是全部答案 —— **打印函数里的每一个字符都有意义**，多余的空白往往正是证据。
2. **遇到"接收不全"先算时间账**：把"字节间隔"和"轮询周期"两个数字写出来对比，比读十遍代码快。
3. **CPU 与外设速度不匹配时，让硬件帮你看门**：中断的触发条件是硬件判断的，不受主循环节奏影响。
4. **改接收机制后，要重新审视所有共享状态**：从轮询改中断，引入的并发问题（清缓冲 vs 中断）是新的风险点。
